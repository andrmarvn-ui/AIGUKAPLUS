# AIGUKA V10 runtime audit

Audit date: 2026-08-06 (Asia/Ho_Chi_Minh)

This document classifies runtime components by actual production dependency. A version prefix alone is not a reason to delete a component: compatibility components remain only when current traffic or reporting still depends on them.

## Active V10 customer runtime

These components own the live customer flow and must remain single-authority:

- `v10-direct-core-worker.js` — builds customer context and prepares AI decision work.
- `v10-ai-worker.js` — stable entrypoint that installs transport adapters and imports `v10-ai-worker-final.js`.
- `v10-ai-worker-final.js` — committed, checksummed AI scheduler/provider implementation (`v10_ai_quality_guard_v12`).
- `v10-outbound-worker.js` — the only active Messenger delivery worker.
- `v10-decision-queue-janitor.js` — stale/superseded queue hygiene only.
- `v10-customer-profile-worker.js` — profile-only enrichment, no outbound path.
- `v10-mode-compat-worker.js` — imports legacy admin Page modes into Core only when stable values change.
- `v10-server-release.js` / `server-v10-final.js` — verify and start the committed Railway HTTP server without source rewriting.

## Required compatibility components

These cannot be removed yet without replacing their live source contract:

- `v9-legacy-inbox-bridge.js` — required because Meta webhook events currently land in `v8_webhook_inbox` before Core ingestion. It has no outbound authority.
- `v9-reporting-publisher.js` and `v9-reporting-sync-worker.js` — publish privacy-safe Core history into the Reporting read model used for long-range Lead pagination and export.

## Report source cutover

Normal report requests no longer require refreshed ad-performance snapshots:

- `meta-direct-inventory.js` reads current campaign, ad set, ad name and effective status directly from Meta Graph API.
- `v10_report_filter_registry()` scopes Meta calls to Page-linked reporting accounts and preserves mapped historical ads.
- `v10_report_customer_metrics()` reads customer/ad/day counts directly from Core and excludes Page actors.
- `report-handler-v10.js` uses direct Meta inventory/Insights plus Core customer metrics during normal operation.
- `v8_report_ads_test` and `v8_report_daily_test` remain outage fallback only.
- `v8_report_leads_test` remains the Reporting history source for paginated Lead lists and Excel export; names and raw contacts are enriched from Core at read time.

The following duplicate snapshot workers are disabled by default and can run only through explicit emergency opt-in environment flags:

- `v9-reporting-legacy-refresh-worker-v2.js`
- `v9-reporting-conversation-refresh-worker.js`
- `v9-meta-ads-insights-worker.js`
- `v9-meta-ad-page-resolver-worker.js`
- `v9-meta-orphan-ad-resolver-worker.js`

Their source files remain during the observation period so a Meta outage fallback can be rebuilt deliberately. They no longer start automatically.

## Permanently retired in this audit

- V8 customer `webhook-inbox-worker`, AI dispatch, outbound and profile workers can no longer be started by `AIGUKA_V8_BACKGROUND_WORKERS`.
- `v8-v9-mode-sync-worker.js` is no longer started; its replacement suppresses unchanged writes and polls less frequently.
- Unused V7 Pancake service and its runtime source patches were deleted:
  - `v7-pancake-service.cjs`
  - `patch-v7-pancake-classifier.js`
  - `patch-v7-pancake-history.js`
  - `patch-v7-pancake-tag-parser.js`
  - `patch-v7-pancake-tag-final.js`

## Resolved architecture debt

### AI worker runtime patch chain

The live entrypoint no longer executes provider-load-balancer or decision-integrity source patches. The exact worker previously generated by that chain is committed as `v10-ai-worker-final.js`, protected by `v10-ai-worker-final.sha256` and verified during release startup.

The old patch files and `v10-ai-worker-v2.js` remain temporarily as build history only. CI reconstructs the historical output in a temporary directory and requires byte-for-byte equality with the committed final worker. They have no runtime import path.

### HTTP server runtime patch chain

The live process no longer executes `patch-server.js` or `patch-direct-meta-dashboard.js`. Their exact output is committed as `server-v10-final.js`, protected by `server-v10-final.sha256` and verified by `v10-server-release.js` before the server starts.

The old base server and two patch files remain temporarily as build history only. CI reconstructs their output in a temporary directory and requires byte-for-byte equality with the committed final server. They have no runtime import path.

### Report snapshot authority

Direct Meta and Core now own normal report data. Snapshot workers are opt-in fallback only, not parallel authorities.

## Known architecture debt still open

### Feature-module compatibility patches

Several startup patches still repair or extend individual feature modules before the final server imports them, especially Learning, Bot Control, AI Context, Drive/Slide and Mapping. They do not rewrite the final server or AI worker, but source ownership is still split. Each group should be consolidated only after parity tests exist for its UI/API behavior.

### Lead history read model

Long-range Lead pagination/export still uses the Reporting read model. This is intentional: Core owns live identity/contact truth, while Reporting stores privacy-safe historical rows. Publisher and sync cannot be removed until a direct Core history API provides equivalent pagination and export performance.

### Legacy schema names

Core tables and several RPCs retain `v9_`/`v8_` names for schema compatibility. Names alone do not create duplicate runtime authority. Rename/drop work should occur only after callers and migrations are cut over.

## Production evidence used for decisions

- The legacy webhook inbox processed 791 events in the previous 24 hours with no pending/error rows, so its bridge remains required.
- Current V10 job queue had completed or superseded work only; no active dead-letter backlog was observed.
- Historical delivery constraint and Meta `#551` error bursts had stopped before this audit; current delivery bundles continue to be sent.
- The old mode-sync worker reported page changes every poll because it compared JSON containing a newly generated timestamp. The V10 compatibility worker removes volatile timestamps from equality checks; production subsequently reported `changed_pages: 0` and `runtime_changed: false`.
- Provider configuration remained present after restart. An empty provider list in the AI heartbeat occurred before any post-restart decision job; the worker loads provider rows lazily when it has work to process.
- The static report registry resolves two active Pages, two configured reporting accounts (`fff` and `Nguyệt Bếp`) and 81 mapped ads without scanning performance facts.
- The direct Core report RPC returned 71 grouped rows for a seven-day sample, totaling 1,445 customers, 145 contacts and 2,902 customer events while snapshot worker heartbeats remained stale.
